# Deployment Types / Kubernetes Deployment Strategies / Zero Downtime Deployment Types
| #SNo| #Type  | #Description |
| :--- | :--- | :--- |
| 1| Canary Deployment |1. Rolling it out to a subset of users before rolling out to all users<br>2. Canary deployments allow organizations to test in production with real users and use cases and compare different service versions side by side<br>3. It's cheaper than a blue-green deployment because it does not require two production environments<br>4. Canary deployment exposes a small percentage of users to the new version initially, which means that they may encounter issues as you iterate on the release<br> Imagine two identical servers, one live and one backup. With Blue Green Deployment, you update the backup server first, then seamlessly switch them. This way, your users never experience downtime!<br> This method is like a test drive for your new features. It releases them to a small group of users first, so you can see how they work before rolling them out to everyone  |
| 2| Blue/Green Deployment (Red/Black Deployment) | 1. Environment isolation between old & new application versions<br>2. Blue-green deployments are an all-or-nothing approach |
| 3|Recreate Strategy Deployment(highlander ) | |
| 4|Shadow Deployment | |
| 5|A/B testing Deployment |Ever wondered which version of a feature is better? This method lets you test two different versions with different users and see which one they prefer. This helps you make data-driven decisions about your software |
| 6|Rolling Deployment | |
| 7|Multi Service Deployment |Want to update multiple services at once? This method handles it! It ensures all services evolve together, minimizing compatibility issues and keeping everything in sync |
| 8|Feature Flags |Imagine a switch that turns features on and off. That's what Feature Flags are! They let you control which features are available to users, so you can experiment with new features without everyone seeing them |
